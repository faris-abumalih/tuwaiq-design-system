# نظام تويق التصميمي (Tuwaiq DS)

أنت تبني داخل نظام تصميمي **مُلزَم ومفحوص آليًا**. هوك `PreToolUse` يرفض أي كتابة ملف تخالف
القواعد الصلبة تحت. الالتزام ليس اختياريًا، وليس مسألة ذوق — القيمة الوحيدة المسموحة هي التوكن.

**المصدر الوحيد للحقيقة:** `${CLAUDE_PLUGIN_ROOT}/tokens/tokens.json`
كل شيء آخر (theme.css، الكلاسات، هذه الوثائق) مشتقّ منه.

---

## القواعد الصلبة — مخالفتها = رفض الكتابة

| # | القاعدة | ✗ ممنوع | ✓ الصحيح |
|---|---------|---------|----------|
| 1 | **لا لون خام** | `"#4931af"` · `rgba(0,0,0,.5)` · `bg-[#eee]` | `var(--brand)` · `var(--text-muted)` · `bg-surface` |
| 2 | **لا مقاس خط خارج السلّم** | `fontSize: "13.5px"` · `text-[17px]` | `var(--text-meta)` أو الكلاس `.t-meta` |
| 3 | **لا زاوية خارج السلّم** | `borderRadius: 18` · `rounded-[10px]` | `var(--radius-lg)` · `rounded-lg` |
| 4 | **لا خصائص اتجاهية فيزيائية** | `marginLeft` · `text-left` · `ml-2` · `pr-4` | `marginInlineStart` · `text-start` · `ms-2` · `pe-4` |
| 5 | **لا عناصر HTML خام للتفاعل** | `<button>` `<input>` `<select>` `<table>` | مكوّنات النظام (انظر `references/components.md`) |
| 6 | **لا نص عربي في الكود** | `<h1>الفعاليات</h1>` | `t("events.title")` + `locales/ar/translation.json` |
| 7 | **لا خط مكتوب يدويًا** | `fontFamily: "'IBM Plex'…"` | `var(--font-family)` |

**تنبيهات (لا تحجب، لكن صحّحها):** مسافة خارج السلّم · ظل خارج التوكنز · `dir="rtl"` ثابت.

**الاستثناء النادر** — لون علامة تجارية خارجية مثلًا:
```tsx
background: BRAND_HEX, // ds-allow: no-raw-color — لون منصة X الرسمي، مثبّت في هويتها
```
السبب إجباري. بدون سبب مكتوب، الاستثناء لا يُقبل.

## مسار العمل — اتبعه بالترتيب

### 0. بطاقة القرارات — إلزامية قبل أي كود

**اقرأ `references/design-thinking.md` وجاوب الستة كتابةً، واعرضها على صاحب الطلب
قبل ما تكتب مكوّنًا واحدًا.** الشاشة التي تُكتب بلا بطاقة قرارات تكون ترجمة حرفية
لجدول بيانات، مهما كانت توكنزها صحيحة.

```
١. الوزن → الحاوية:  ما وزن هذا الإجراء في المنتج؟ صفحة / مودال / شيت / بوبوفر — ولماذا؟
٢. البطل:            أي حقل يستحق أن يكون عنوان الشاشة نفسه (بلا لابل، بمقاس العنوان)؟
٣. الطي:             أي الحقول لا يمنع غيابها الإنشاء؟ → «خيارات متقدمة» أو صفحة الإعدادات.
٤. شكل الاختيار:      لكل اختيار — شيت كاردات / pills / stepper / دروب داون، ولماذا؟
٥. الدمج:            هل صحّة الإدخال تعتمد على شكله في سياقه؟ → الإدخال داخل المعاينة.
٦. اللحظة:           أي قرار صغير يستحق أن يصير لحظة ممتعة؟ (واحدة أو اثنتان، لا أكثر)
```

**القاعدة الأم:** أهمية الإجراء في المنتج تحدّد حجمه على الشاشة — **لا عدد حقوله**.
إجراء بخمسة حقول قد يستحق صفحة كاملة، وإجراء بثلاثين حقلًا قد يبقى شيتًا.

**ممنوع** حلّ النجمة: أن تعرض كل الحقول وتضع `*` على المطلوب. هذا تهرّب من القرار ٣.

### 1. الرحلة قبل البيانات
ما الذي يريد المستخدم أن يفعله؟ ما القرار الأول؟ ما الذي يُؤجَّل؟
(`references/principles.md` — المبادئ ٩ و١٠ و٢١)

### 2. اختر الشكل قبل الكود
- قرار صغير سريع (وقت، عدد، نوع، لون) → **Popover**
- قرار يحتاج تركيز، فرع من سياق قائم → **Modal**
- تفاصيل وإعدادات كيان موجود → **Side Sheet**
- ركيزة في المنتج → **صفحة كاملة**
- من ٢ إلى ٦ خيارات مؤثرة → **Cards / Pills / Segmented** لا Dropdown
- كيانات لها هوية بصرية → **شيت فيه كاردات بالشعارات + بحث + مخرج «إضافة جديد»**
- بيانات كثيرة + فرز/بحث/إجراءات جماعية → **جدول**، وإلا **لا جدول**

التفاصيل الكاملة: `references/patterns.md`

### 3. اقرأ المرجع المناسب — ولا تخمّن قيمة أبدًا
| تحتاج | اقرأ |
|-------|------|
| **كيف أقرّر شكل الشاشة أصلًا** | `references/design-thinking.md` ← ابدأ من هنا |
| لون، مقاس، مسافة، زاوية، ظل، حركة | `references/tokens.md` |
| أي مكوّن أستخدم وكيف | `references/components.md` |
| تخطيط صفحة، بوبوفر/مودال/شيت، جداول، نماذج | `references/patterns.md` |
| RTL، أرقام، تواريخ، اتجاه، خط عربي | `references/arabic-rtl.md` |
| فارغ / تحميل / خطأ / لا صلاحية / نجاح | `references/states.md` |
| المبادئ الـ٢٥ (لماذا نصمّم هكذا) | `references/principles.md` |
| مشروع جديد من الصفر | `references/new-project.md` |

### 4. ابنِ الحالات، لا الشكل الساكن فقط
كل شاشة تحتاج على الأقل: **فارغة · تحميل · خطأ · محتوى**.
الشاشة بدون حالة فارغة مصمَّمة نصف تصميم (`references/states.md`).

### 5. راجع قبل التسليم
جاوب اختبار القبول في `references/design-thinking.md` (٧ أسئلة)، ثم:
شغّل الفحص بنفسك:
```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ds_lint.py" src
```
ثم امشِ على `references/checklist.md` بندًا بندًا.

## الأمر الوحيد

`/ds <أي طلب>` — نقطة دخول واحدة. يقرأ حالة المشروع، يجهّزه إن لزم، يعرض بطاقة
القرارات، يبني، ثم يفحص ويغلق. لا أوامر منفصلة للتجهيز أو الفحص.

- `/ds صفحة إنشاء مسابقة` → بطاقة قرارات ← موافقة ← بناء ← فحص
- `/ds راجع` → فحص المشروع أو `git diff`
- `/ds أعد التفكير في صفحة الأعضاء` → تشخيص وبطاقة جديدة، بلا كود
- `/ds أي توكن للنص الثانوي؟` → إجابة من المراجع

مراجعة PR عميقة: وكيل `ds-reviewer`.

## حدود النظام

- **لا تخترع توكن.** ما فيه توكن مناسب؟ الحل PR على `tokens.json`، لا قيمة خام في مكوّن.
- **لا تعدّل `theme.css` يدويًا** — هو مولَّد: `python3 scripts/gen_theme.py src/styles/theme.css`.
- **لا تنسخ مكوّنًا وتعدّله.** وسّع المكوّن الأصلي بـ prop، أو أضِف variant للنظام.
- **لا تضف مكتبة UI جديدة** (MUI, AntD, DaisyUI…) — تكسر النظام. المكوّنات من `assets/primitives`.
- **لا تسلّم شاشة بلا بطاقة قرارات.** التوكنز الصحيحة لا تنقذ شاشة قرارها التصميمي غلط.
